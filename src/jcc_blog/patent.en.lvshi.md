ABSTRACT

The present invention discloses a cross-chain state verification method, apparatus, electronic device, and storage medium for blockchain. The method comprises: obtaining a state assertion submitted by a user on a source chain, wherein the state assertion is an assertion regarding verifiable data on the source chain; generating a verifiable credential, wherein the verifiable credential comprises a credential identifier, a decentralized identifier, the state assertion, and a content hash, wherein the content hash is a result of performing a hash operation on the state assertion; digitally signing the verifiable credential based on a user private key corresponding to the decentralized identifier to obtain a digitally signed verifiable credential; and storing the digitally signed verifiable credential in a distributed storage system, such that a user on a destination chain can perform state verification on the verifiable data based on the digitally signed verifiable credential. The method ensures the security of cross-chain data state verification between the source chain and the destination chain.

BACKGROUND ART

A blockchain is a decentralized network composed of distributed multiple nodes. Blockchain interoperability is a core infrastructure challenge currently facing the Web3 ecosystem. With the parallel development of heterogeneous blockchains (Ethereum, Bitcoin, Solana, Polygon, Arbitrum, etc.), the demand for cross-chain communication is increasing. Existing cross-chain communication for blockchains is implemented through centralized cross-chain bridges, oracle networks, light client verification, and other methods. These methods have issues such as collusion or other risks in cross-chain state verification, resulting in low security.

Embodiments of the present invention provide a cross-chain state verification method for blockchain. This method is applicable to mobile phones, computers, or other electronic devices capable of accessing blockchain nodes. For ease of understanding, the following provides a brief description of key technical terms involved in this method.

Content Addressing (hereinafter referred to as "CA") refers to generating globally unique identifiers through cryptographic hashes of content, rather than through location addresses, thereby achieving data immutability and verifiability.

Verifiable Credentials (hereinafter referred to as "VC") refer to W3C standardized digital credential formats containing assertions, signatures, metadata, etc. They are cryptographically signed digital credentials possessing verifiability, immutability, and self-sovereignty.

Decentralized Identifiers (hereinafter referred to as "DID") are blockchain-based globally unique, user-controlled identity identifiers that do not rely on centralized registration authorities and support verifiable assertions and distributed identity management.

Byzantine Fault Tolerance (hereinafter referred to as "BFT") is a distributed consensus mechanism that allows consensus to be reached in the presence of malicious or faulty nodes. It possesses high fault tolerance and strong consistency, and is suitable for collaborative verification and state synchronization among multiple heterogeneous chains in cross-chain scenarios.

Proof Systems (hereinafter referred to as "PS") are cryptographic protocols for generating succinct, efficient, and verifiable proofs of computational integrity. Through standardized signature algorithms such as ECDSA and EdDSA, they implement lightweight zero-knowledge proofs (zk-SNARKs/zk-STARKs), ensuring the privacy and efficiency of cross-chain verification.

Source Chain refers to the initiating blockchain in cross-chain operations, which is the chain where original data, assets, or states reside. It primarily provides factual information that needs to be verified or transmitted (such as user assets, identity assertions, transaction records, etc.). Destination Chain refers to the receiving blockchain in cross-chain operations, which is the chain where applications that need to verify or use source chain information reside. It primarily obtains trusted facts from the source chain through cross-chain verification mechanisms and executes business logic based on these facts.

Embodiments of the present invention provide a cross-chain state verification method for blockchain. This method is applicable to electronic devices. As shown in FIG. 1, the cross-chain state verification method for blockchain comprises:

S101: Obtaining a state assertion submitted by a user on a source chain, wherein the state assertion is an assertion regarding verifiable data on the source chain;

S102: Generating a verifiable credential, wherein the verifiable credential comprises a credential identifier, a decentralized identifier, the state assertion, and a content hash; the content hash is a result of performing a hash operation on the state assertion; the digital signature is a result of digitally signing the content hash based on a user private key corresponding to the decentralized identifier;

S103: Digitally signing the verifiable credential based on a user private key corresponding to the decentralized identifier to obtain a digitally signed verifiable credential;

S104: Storing the digitally signed verifiable credential in a distributed storage system, such that a user on a destination chain can perform state verification on the verifiable data based on the digitally signed verifiable credential.

As an example, in step S101, the electronic device may receive a state assertion published by a user based on verifiable data on the source chain, for example, "I own NFT #1234", "I own 100 USDT", "I am a DAO member", etc. The verifiable data herein is objectively existing verifiable on-chain data on the blockchain.

In one embodiment, the verifiable data includes smart contract states, transaction history data, event logs, and on-chain state data. Smart contract states can be directly verified by calling smart contract interfaces, for example, NFT ownership that can be verified through the NFT contract's ownerOf(tokenId), token balances that can be verified through the ERC20 contract's balanceOf(address), etc. Transaction history data can be verified by querying blockchain historical transaction data, which can be an account's historical transaction records, fund flows, participated DeFi protocols, etc. Event logs can be verified by querying transaction receipts, for example, event logs and operation records generated by smart contracts. On-chain state data can be verified by querying state mapping data, for example, account permissions, governance rights, community membership, etc. In this example, since the state assertion is a scenario regarding verifiable data on the source chain, any third party can directly verify the truthfulness of the state assertion on the source chain, making fraud impossible to conceal and ensuring the security of cross-chain communication.

As an example, in step S102, the electronic device uses a pre-configured target hash algorithm to perform a hash operation on the state assertion to determine the content hash corresponding to the state assertion. The target hash algorithm is an algorithm for performing hash operations on this state assertion, for example, but not limited to, the SHA-256 algorithm. This content hash serves as a unique digital fingerprint of the state assertion, used to identify the uniqueness and integrity of data, ensuring that data cannot be tampered with. Subsequently, following the W3C DID and Verifiable Credential international standards, a verifiable credential is generated based on the state assertion and content hash. This verifiable credential carries information such as credential identifier, decentralized identifier, source chain identifier, state assertion, content hash, and generation timestamp, ensuring immutability and traceability. The credential identifier is an identifier for uniquely identifying the verifiable credential. Each verifiable credential is equipped with a globally unique credential identifier (vcId). After the destination chain's smart contract uses this verifiable credential to execute business logic, the credential identifier is marked as used, preventing multiple uses and replay attacks of the same credential. The decentralized identifier is an identifier for uniquely identifying user identity. The source chain identifier is an identifier for uniquely identifying the source chain where the verifiable data resides. The generation timestamp refers to the timestamp when the verifiable credential was generated.

As an example, in step S103, the electronic device may use the user private key corresponding to the decentralized identifier to digitally sign the verifiable credential, obtaining a verifiable credential carrying a digital signature, such that users on the destination chain can decrypt the digitally signed verifiable credential based on the user public key corresponding to the decentralized identifier, ensuring the reliability of subsequent verification. For example, the electronic device may perform EIP-712 signature on the verifiable credential based on the user private key corresponding to the decentralized identifier: sig = Sign(VC, userPrivateKey), and store the digitally signed verifiable credential in a distributed storage system, such that the destination chain can retrieve, verify, and anchor the authenticity and timeliness of this verifiable credential in real-time. The distributed storage system uses a content addressing mechanism, specifically but not limited to InterPlanetary File System (hereinafter referred to as "IPFS"). After the state assertion of the verifiable credential is determined, its content hash can be deterministically calculated, giving it characteristics such as decentralized storage, global accessibility, and low storage costs.

In this example, storing the digitally signed verifiable credential in a distributed storage system, such that users on the destination chain can perform state verification on verifiable data based on the digitally signed verifiable credential, provides the following three anti-fraud mechanisms: First, since all verifiable credentials on IPFS possess immutable content hashes, validators must verify the consistency between the content hash of the verifiable credential stored in IPFS and its state assertion content before verification. Any modification to the verifiable credential will cause the content hash in IPFS to change, immediately being detected as fraudulent. Therefore, the content hash serves as a content fingerprint of the verifiable credential, preventing the verifiable credential from being tampered with in transit. Second, since verifiable credentials stored in IPFS all carry digital signatures, and the digital signatures are associated with the user private key corresponding to the decentralized identifier, anyone can verify the authenticity of the signature through ECDSA signature recovery. If the signature does not match or the signer is incorrect, it is immediately determined to be fraudulent, thereby confirming that the verifiable credential originates from the user themselves, preventing identity forgery. Third, since the state assertion in the verifiable credential is an assertion regarding verifiable data on the source chain, any third party can directly query the source chain to verify the truthfulness of the state assertion. Users cannot commit fraud through concealment, forgery, or tampering, making the on-chain verification process transparent and user fraud easily detectable.

In this embodiment, by performing a hash operation on the state assertion corresponding to verifiable data on the source chain, rather than on the verifiable data itself, the content hash is determined, and then a verifiable credential is generated based on the state assertion and content hash. This makes the integrity of the verifiable credential require no additional verification mechanisms, as any change in content hash automatically invalidates it. Different signature algorithms can be used to digitally sign the verifiable credential based on the user private key, adapting to different blockchain environments. Storing the signed verifiable credential in a distributed storage system eliminates the need to transfer or copy verifiable data to the distributed storage system, reducing storage costs. Through decentralized storage of signed verifiable credentials in a distributed storage system, there is no single point of failure, and validators from any region can independently access and verify the verifiable credential.

As an example, in step S201, the electronic device may receive a cross-chain business request submitted by a user on a destination chain. This cross-chain business request refers to an operation instruction initiated by the user that needs to be collaboratively completed between the source chain and destination chain, such as cross-chain asset transfer, identity information verification, or contract state synchronization. This request embeds a unique business identifier and a verifiable credential carrying a digital signature, ensuring that the business context is traceable, the credential source is verifiable, and the operation intent is immutable. This business identifier is used to uniquely indicate the business operation that needs to be executed by the destination chain contract. For example, when a Polygon game needs to verify a user's Ethereum NFT, Polygon is the destination chain, Ethereum is the source chain, and the business identifier points to the "NFT ownership verification" operation. The verifiable credential is issued on the Ethereum chain, stored via IPFS and anchored to the CID hash on Ethereum, with its content hash and state assertion together constituting a lightweight verification anchor.

As an example, in step S202, after receiving the cross-chain business request, the electronic device may randomly select one or more validators from a validator pool and broadcast a verification request carrying the credential identifier to them. The validators access the distributed storage system based on the credential identifier, determine the digitally signed verifiable credential corresponding to the credential identifier, parse the verifiable credential, determine the credential identifier, decentralized identifier, source chain identifier, state assertion, content hash, generation timestamp, and other information it carries, in order to perform verification based on the parsed information, obtain the corresponding verification result, and return the verification result to the electronic device that triggered the verification request on the destination chain.

The executable condition refers to a pre-configured condition for evaluating whether the business operation can be executed.

As an example, in step S203, the electronic device collects verification results returned by each validator. When the verification results satisfy the executable condition, the business operation corresponding to the business identifier can be executed, including but not limited to authorization access control, credit score calculation, qualification review, voting right allocation, etc., all without transferring or locking source chain assets. In this example, executing the business operation corresponding to the business identifier specifically includes: conditional judgment (if VC.validity == true then ...), state update (authorization, point calculation, etc.), and cross-chain interaction (triggering other contracts on the destination chain), among other operations.

In this example, when an application on the destination chain needs to use a certain verifiable credential, for example, when a Polygon game needs to verify a user's Ethereum NFT, the user or a user on the destination chain needs to send the digitally signed verifiable credential from IPFS to the destination chain contract. The destination chain contract verifies the verifiable credential, determines the verification result, and then determines whether to execute the business operation based on the verification result.

If the signature does not match or the signer is incorrect, it is immediately determined to be fraudulent, thereby confirming that the verifiable credential originates from the user themselves, preventing identity forgery. Third, since the state assertion in the verifiable credential is an assertion regarding verifiable data on the source chain, any third party can directly query the source chain to verify the truthfulness of the state assertion. Users cannot commit fraud through concealment, forgery, or tampering, making the on-chain verification process transparent and user fraud easily detectable. When verification results from all validators satisfy the executable condition, executing the business operation corresponding to the business identifier helps ensure the security of cross-chain business operations.

As an example, the electronic device may dynamically determine the required number of validators based on the business type of the business identifier, such as experience value and network level, for example, high-risk asset transfers require more than 10 validators, while identity verification only requires 5. Subsequently, validators matching the required number of validators can be randomly selected from the validator pool, and a verification request carrying the credential identifier is broadcast to them. The validators independently parse the signature, content hash, and other content in the verifiable credential to obtain the corresponding verification result.

If the two are inconsistent, it indicates that the verifiable credential has been tampered with, and the integrity verification result is determined as verification failed. In this example, since all verifiable credentials carry immutable content hashes, validators prevent verifiable credentials from being tampered with in transit by verifying the consistency between the content hash and its state assertion content.

As an example, the electronic device may parse the verifiable credential to determine the decentralized identifier DID and digital signature in the verifiable credential. The digital signature is generated by signing the content hash of the verifiable credential using the user private key. The corresponding DID document can be queried based on the decentralized identifier DID to extract the corresponding user public key. Standardized algorithms (such as ECDSA or EIP-712) are used to verify whether the signature was generated by the user's private key, and the signer's identity is confirmed through public key recovery mechanism. If the digital signature matches the user public key, the signature verification result is determined as verification passed. If the digital signature does not match the user public key, the signature verification result is determined as verification failed. In this example, the ECDSA (Elliptic Curve Digital Signature Algorithm) recovery mechanism can be used to verify whether the digital signature was generated by the user private key. Since all verifiable credentials carry digital signatures, and the digital signatures are associated with the user private key corresponding to the decentralized identifier, anyone can verify the authenticity of the signature through ECDSA signature recovery, thereby confirming that the verifiable credential originates from the user themselves, preventing identity forgery.

As an example, the electronic device may parse the verifiable credential to determine the state assertion and source chain identifier in the verifiable credential, and determine the verifiable data pointed to by the state assertion. If the two are consistent, the state assertion is determined to be a truthful assertion, and the state verification result can be determined as verification passed. If inconsistent, the state assertion is determined to be a fraudulent assertion, and the state verification result can be determined as verification failed. In one embodiment, the verification consensus condition comprises: a consensus ratio being greater than a consensus ratio threshold corresponding to the business identifier;

As an example, when the electronic device determines that the voting quantity verification result is verification passed, it also counts the number of verification results indicating verification approval, calculates the ratio of the number of verification results indicating verification approval to the number of voting validators to determine the consensus ratio, and compares the consensus ratio with the consensus ratio threshold. When the consensus ratio is greater than the consensus ratio threshold, it is determined that the verification consensus condition is satisfied. Conversely, when the consensus ratio is not greater than the consensus ratio threshold, it is determined that the verification consensus condition is not satisfied, and the process can be terminated directly. In this example, the validator quantity threshold and consensus ratio threshold corresponding to different business identifiers can be flexibly determined to adapt to the needs of different business operations.
